1. WHAT THIS IS
--------------------------------------------------------------------------------

A production Hindi/multilingual AI voice calling agent. It phones people, holds a
real conversation, scores the outcome, and reports it.

Live at https://www.qsilon.com

The main script is "Roshini", an EMI collections agent for Bajaj Auto Credit.
Three other scripts exist in the same deployment: real estate, e-commerce
delivery confirmation, and salon booking.

One client today. When more arrive the plan is a SEPARATE DEPLOYMENT per client
(own Render service + own Mongo database), NOT multi-tenancy in one instance.
That decision was made deliberately - see section 9.

4. ARCHITECTURE - HOW ONE CALL WORKS
--------------------------------------------------------------------------------

  BEFORE THE CALL
    Upload list  ->  Create/launch a run  ->  Dials 5 at a time

  DURING THE CALL
    Customer <-> Vobiz (PSTN) <-> Qsilon agent (FastAPI on Render)

    Every turn, in this order:
      Deepgram nova-3      hears the words        ~300 ms
      Gemini flash-lite    decides the reply      ~600 ms
      Cartesia sonic-3     speaks it back         ~120 ms
      -> caller waits about 800 ms

  AFTER THE CALL
    Score it (Gemini, ~1.6s)  ->  MongoDB  ->  Report CSV (20 columns)

KEY FILES
    api.py                 all HTTP + WebSocket endpoints, startup tasks
    call_handler.py        one live call: audio, VAD, STT, LLM, TTS, hangup
    campaign_service.py    bulk runs, retries, calling hours, scoring rules
    db_service.py          every Mongo access
    stt_stream_service.py  the Deepgram streaming socket
    vobiz_service.py       Vobiz REST + AudioStream
    template_service.py    resolves prompt/greeting/voice per use case+language
    frontend/src/          React console

5. MEASURED PERFORMANCE (real logs, not estimates)
--------------------------------------------------------------------------------

    Greeting first audio     130-176 ms
    Greeting total           577-630 ms
    Turn latency             688-845 ms   <- the target, achieved
    Median call              56 s, ~7 turns
    Answer rate              72%  (64 spoke, 25 not reached of 89)

  HOW IT GOT THERE (it started at 4810 ms):
    - Gemini free tier was throttling at 10-15 requests/minute. Paid tier fixed
      the cause.
    - A hedge race fixed the effect: the backup model starts 0.5s in, ALONGSIDE
      the primary, and the first usable answer wins. Do not raise this window -
      it was tried at 1.5s and turns went to 2107 ms.
    - The backup's HTTPS connection is opened during the greeting. Before that,
      the first hedge of every call paid a TLS handshake: 963 ms vs 467 ms.

  COSTS PER CALL-MINUTE (Rs 88/USD)
    Telephony (Vobiz)     1.00
    TTS (Cartesia)        1.42
    STT (Deepgram)        0.65
    LLM (Gemini)          0.11
    ------------------------
    Total variable        3.18   (+ Rs 620/month hosting)

    100 real-estate leads: ~25 minutes, ~Rs 335, ~73 real conversations.

  NOTE ON THE PROMPT: prompt SIZE is not a latency lever. Measured: a 2992-char
  prompt gave 1053 ms median, a 237-char prompt gave 968 ms. About a second is
  what the model costs from India - round trip and generation, not prompt length.

9. ARCHITECTURE DECISION - MULTIPLE CLIENTS
--------------------------------------------------------------------------------

The system today is SINGLE CLIENT, multiple use cases. What would break with a
second client:

  - templates[0] is hardcoded in 4 places - only one prompt template is ever read
  - one global disposition list
  - one global app_settings: one voice, one from_number, one telephony account
  - NO client/tenant field on any record (sessions, campaigns, datasheets)

RECOMMENDATION MADE AND ACCEPTED: one deployment per client until roughly 8-10
clients. Reasons: zero risk of one client's debtor data reaching another (the
worst possible failure with this data), each client gets their own caller ID and
limits, and it needs no code change. Rs 620/month per client is trivial against
Rs 335 per 100 calls.

Multi-tenancy becomes worth building only when hosting and operating several
deployments costs more than the engineering would.

10. HOW THE USER WORKS - READ THIS
--------------------------------------------------------------------------------

  - The user writes in Hinglish. Reply in Hinglish. Keep it direct.
  - They move fast and often send a new instruction mid-task. Finish what is in
    flight, then take the new one.
  - THEY PUSH, NOT CLAUDE. Commit and tell them to push.
  - They send Render logs and screenshots as evidence. READ THEM CAREFULLY -
    several real bugs in this project were found only in a log, and several
    wrong guesses were avoided by waiting for one.

  WHAT WORKED, AND SHOULD CONTINUE:
  - Measure before changing. Every latency claim in this document came from a
    real log or a benchmark against the live model, not an estimate.
  - When a guess is a guess, say so. Twice in this session a confident-sounding
    theory was wrong, and saying "I do not know yet, send the log" was faster.
  - Verify against the live database where safe. Reading production Mongo to
    check a fix is fine; writing to it needs care.
  - Own mistakes plainly. Three real ones happened here:
      * update_model_data replaced instead of merging and wiped the analysis on
        82 sessions (restored by re-scoring, transcripts were intact)
      * adding "hello" to a filler list killed a whole call's transcripts
      * an undefined name (analysis_prompt) broke ALL bulk calling from 23 Aug
        to 6 Sep, silently, because a gather swallowed the exception
  - Small commits with a message that says what was wrong and what the evidence
    was. The history is the explanation.

  A WARNING FROM EXPERIENCE:
  Running CallHandler.initialize() against the production database CREATES A
  JUNK SESSION. Doing this in diagnostics polluted the client's Conversations
  list with 7 fake calls. It is fixed now (boot passes persist_session=False),
  but be careful what you run against production.

11. USEFUL COMMANDS
--------------------------------------------------------------------------------

  Build the frontend (ALWAYS before committing frontend changes):
      cd frontend && npm run build

  Type-check only:
      cd frontend && npx tsc -b

  What is not yet pushed:
      git log --oneline origin/main..HEAD

  Read production data safely (loads .env.render, read-only):
      python - <<'PY'
      import re, io, os, asyncio, logging
      for ln in io.open('.env.render', encoding='utf-8'):
          m = re.match(r'^([A-Z_]+)=(.*)$', ln.strip())
          if m: os.environ.setdefault(m.group(1), m.group(2))
      logging.disable(logging.CRITICAL)
      import call_handler as ch
      async def main():
          h = ch.CallHandler(); await h.db.initialize()
          print(await h.db.sessions.count_documents({}))
      asyncio.run(main())
      PY

  NOTE: do NOT call h.initialize() in a script - it writes a session row.
  Use h.db.initialize() instead.
